# 08 — Security & Multitenancy

## Identity & access
- **AuthN:** OIDC (any IdP: Entra ID, Okta, Google, Keycloak), SAML for enterprise tier, built-in email+password with TOTP/WebAuthn for solo/team. SCIM provisioning (enterprise).
  - *Shipped (WP-1.9):* password+TOTP and OIDC authorization-code flow with PKCE, as two implementations of one `AuthProvider`. ID-token signatures are verified against the issuer's JWKS with a closed algorithm allowlist and no symmetric or `none` path ([ADR-019](adr/ADR-019-jose.md)). **The IdP authenticates; it never authorizes** — group and role claims are deliberately not read, and an assertion cannot provision a user: it links to an account an administrator already created, matching a verified email once and thereafter the subject. One IdP per deployment; per-tenant provider configuration waits on the secrets vault below. Sessions, device binding, refresh and revocation are identical on both paths, so an IdP outage cannot become a privilege question.
  - *Shipped (WP-1.12):* **TOTP enrollment**, without which the "+TOTP" above described a code path no user could switch on. Self-service at `/api/v1/me/totp/*` (no route takes a user id — enrollment acts on the caller and nobody else): enroll re-authenticates with the password, then issues a pending secret with an `otpauth://` URI and a QR ([ADR-020](adr/ADR-020-qr-encoding.md)) — a session alone must not be able to add a factor the account owner does not hold; confirm validates a code against it, enables the factor, burns the matched step so the confirmation code is not also a login code, and returns ten single-use recovery codes. Recovery codes are 120 bits of `crypto/rand` stored as SHA-256, single-use by `UPDATE … WHERE used_at IS NULL` so two concurrent logins cannot double-spend one, and offered at login in their own field rather than told apart from a TOTP code by shape. Disabling requires the password **and** a second factor — a recovery code counts, since the user who needs to disable is usually the one whose authenticator is gone — because the threat is a session an attacker holds, not a password they know. A second factor locks for 15 minutes after 10 consecutive failures: the gateway's 100 req/s budget would otherwise break a ±1-step TOTP window in under an hour for anyone who already has the password. Every transition is audited (INV-T4). TOTP secrets remain plaintext at rest, unchanged since WP-0.3 and blocked on the secrets vault below.
- **Principals:** users, service principals (integrations, AI agents), device tokens (sync clients). All access through short-lived tokens; refresh bound to device.
- **AuthZ: RBAC + row-level rules.** Roles bundle permissions of shape `(object, action, condition)` where condition is an optional CEL expression over record + actor (e.g., `record.owner == actor.id || actor.team in record.team`). Permission floors from core cannot be lowered by overlays (ADR-006). Field-level read/write masks for sensitive fields (salary, bank details).
  - *Shipped (WP-3.3a):* conditions are **evaluated**, having been stored-but-unevaluated since WP-0.3. CEL comes from `cel.dev/cel-go` in a closed environment — two bindings (`record`, `actor{id,tenant,roles}`), no extension functions, no host state, no clock, no network — wrapped by `kernel/expr`, which is the only package permitted to import it ([ADR-022](adr/ADR-022-expression-language.md), asserted by a test). An expression is compiled at grant time, so a rule that does not compile or does not answer with a boolean is refused where the administrator can see it rather than denying every request in silence.
  - **A condition can only narrow (INV-T3), structurally.** It is consulted *after* a matching grant is found, never instead of one, and every failure mode — false, evaluation error, cost-budget overrun, non-boolean result, an expression that no longer compiles — denies that grant. So the guarantee does not rest on the evaluator being semantically correct. A record-less gate (`Can`/`Authorize`, and the `GrantedObjects` call that computes a sync replica's scope) is therefore satisfied by **unconditional grants only**: it has no record to judge, and treating a conditional grant as sufficient there is exactly the widening INV-T3 forbids. Record-bearing writes go through `AuthorizeGrants` + `GrantSet.Allow`, evaluated inside the transaction that does the writing.
  - Conditions attach to `create`, `update` and `delete` today. On `read` — and on any other action — a condition is **refused at grant time**, naming the WP that owns the missing half, rather than stored and never consulted: row-level filtering of list and sync reads needs the predicate pushed into the query with a paging story for the rows it rejects. A condition guards *which rows you may touch*, not *what they may become* (Postgres RLS's `USING`, not its `WITH CHECK`).
- **Approvals:** kernel approval-request service (used by AI gates, payment runs, PO thresholds); N-eyes configurable.

## Tenant isolation (ADR-005)
- Postgres RLS on every tenant table; session `app.tenant_id` set by middleware from the token — never from request params.
- CI gate: the "no-context query returns zero rows" test suite; static check that every new table has tenant_id + RLS policy.
- Per-tenant: rate limits, statement timeouts, storage quotas, connection budgets.

## Data protection
- TLS everywhere; HSTS; modern cipher suites only. The CSP is strict and not configurable, with one deliberate relaxation: **`script-src` carries `'wasm-unsafe-eval'`**, without which the browser refuses to instantiate the SQLite-WASM replica (ADR-017) and the entire offline client is dead in the shipped app — which is exactly what shipped until WP-2.7 found it. It permits WebAssembly compilation only; it does *not* restore `eval()`, `new Function()` or any string-to-JavaScript path, which is why it is a separate keyword and why `'unsafe-eval'` would have been a real weakening rather than a bigger version of the same thing.
- At rest: disk/volume encryption assumed; field-level encryption (kernel envelope encryption, keys in KMS/age file for self-host) for designated sensitive fields.
- **Client replicas — the controls differ by shell, and this line used to overstate them.** It read *"SQLite encrypted (SQLCipher/OS keystore-derived key) … encryption is the real control"*, which was written before [ADR-017](adr/ADR-017-sync-client-core.md) fixed the browser client on SQLite-WASM's SAH-pool VFS. There is no OS keystore in a browser and no cipher in that VFS, and the gap is not a missing library: SAH-pool's `xRead`/`xWrite` are synchronous while WebCrypto is async, so a page cipher needs extractable key bytes in JS memory — sitting next to the ciphertext, reachable by the same thief. [ADR-021](adr/ADR-021-replica-at-rest-encryption.md) resolves it:
  - *Browser shell (today):* **scoped replicas** (a device replicates only what its principal may read — WP-2.4), **remote wipe honored at the next authenticated request** (WP-2.5, INV-D1), device registration and revocation, short-lived device-bound tokens, and the operating system's own full-disk encryption, which is where whole-device protection legitimately lives for a browser client.
  - *Native shells (Tauri desktop/mobile, WP-4.8):* at-rest encryption of the replica with an OS keystore-derived key. This is where the original sentence becomes true, and it is tracked as a numbered work package rather than an aspiration.
  - *Documented limit, unchanged and now the honest one:* a stolen device that never reconnects keeps what it holds, and on the browser shell that data is protected by the OS's disk encryption rather than by ours. A wipe is delivered, never confirmed — the server can prove it refused the device and told it why; it cannot prove erasure on a disk it does not own.
- **Secrets vault for connector/plugin credentials — *shipped (WP-3.0)*.** `kernel/secrets`: every value is sealed with AES-256-GCM under a data key minted for that one secret, and the data key is stored wrapped by the deployment's key-encryption key (`LASTERP_SECRETS_KEYFILE`, docs/09). That per-secret data key is what makes key rotation a re-wrap of one short column rather than a decrypt-and-re-encrypt of every payload. Both seals bind their row as AAD (tenant + name, and for the wrapped key the key id), so a row lifted into another tenant by a restore or a hand-edited backup fails to open rather than decrypting into the wrong place — defence in depth under INV-T1, whose primary enforcement stays RLS. The whole of it is **INV-K1** (docs/19).
  - **No route returns a secret's value, and that is a design constraint rather than an omission** ([WP-3.0-decisions.md](notes/WP-3.0-decisions.md) §4). The API stores, lists metadata and deletes; the person who set a credential already holds it, and a reveal endpoint is a credential-exfiltration API reachable with one stolen session. A repo test enumerates the live mux and fails if one appears.
  - Reads happen server-side through `secrets.Get`, which requires a **named reader** (`module:oidc`, `plugin:com.acme.x`) and audits the read in the same transaction (INV-T2/T4). The capability *grant* check — the manifest's `secrets:` list — is the `Grants` seam WP-3.1 fills; until a plugin host exists there is no untrusted reader to gate, and INV-X1 is not claimed early.
  - A secret is a kernel table, not a metadata object, so it is structurally absent from the change feed, the sync API, every client replica and every export — not filtered out of them.
  - Still plaintext at rest and named here so it is not forgotten: **TOTP secrets** (per-user column encryption, a different shape from a keyed store — decisions §9) and the **deployment-level OIDC client secret**, whose per-tenant successor this vault now unblocks.
- PII tagging in metadata → drives export redaction, retention policies, GDPR erasure workflow (erasure of PII on CRUD objects; event payload crypto-shredding for event-sourced ones).

## Audit & compliance posture
- Three immutable trails: event store (financial), audit_log (master data), agent_audit (AI). Append-only, exportable, hash-chained per day for tamper evidence.
- Compliance-friendly defaults: double-entry integrity, period close with locks, correction-by-reversal, sequential document numbering per jurisdiction rules, 4-eyes on payments. Full compliance architecture — GDPR/CCPA privacy engine, ISO 27001/27701/SOC 2 controls matrix, DoD tier (NIST 800-171/CMMC, FIPS 140-3, air-gap) — in [20-COMPLIANCE-PRIVACY.md](20-COMPLIANCE-PRIVACY.md).

## Supply chain & platform hardening
- Plugins: signed bundles, capability review at install, sandbox (ADR-007). Dependencies: pinned + `govulncheck`/`npm audit` in CI; SBOM published per release.
- Standard web hardening: CSP, output encoding, parameterized SQL only (enforced by construction — the metadata engine emits parameterized queries), CSRF tokens on browser sessions, upload scanning hooks.
- `SECURITY.md` + coordinated disclosure; secrets scanning in CI.

## Threat model highlights (full doc grows in tools/threat-model.md)
| Threat | Control |
|---|---|
| Cross-tenant leak via app bug | RLS as backstop + CI gates |
| Malicious plugin | WASM sandbox, capabilities, no ambient authority, audit |
| Rogue/compromised AI agent | Role limits, budgets, approval gates, kill switch, dedicated audit |
| Offline device theft (browser shell) | Scoped replicas, remote wipe at next connect, device revocation, short-lived device-bound tokens, **OS disk encryption** — *not* in-page replica encryption, see Data protection above and [ADR-021](adr/ADR-021-replica-at-rest-encryption.md) |
| Offline device theft (native shells, WP-4.8) | The above **plus** replica at-rest encryption with an OS keystore-derived key |
| Sync replay/forgery | Device-bound tokens, command_id dedupe, server revalidation |
| Insider financial fraud | Immutability, 4-eyes approvals, anomaly detection, hash-chained trails |
