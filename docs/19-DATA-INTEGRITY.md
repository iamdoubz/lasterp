# 19 — Data Integrity: The Paramount Requirement

**Founding requirement (Dan, 2026-07-07):** data integrity is paramount. No new feature, AI enhancement, or plugin may be able to ruin the integrity of our data — and this must be proven by exhaustive tests, not promised by review.

This doc consolidates integrity guarantees scattered across ADR-003/005/007/014 into one enforceable system: a numbered **invariant catalog**, four **enforcement layers**, and the **Integrity Gauntlet** — a CI stage that every change, human- or AI-authored, must pass.

## 1. The invariant catalog (numbered, versioned, machine-checked)

Every invariant below has: an ID, an enforcement layer, a test suite tagged with its ID, and a runtime sentinel where applicable. New modules MUST register their invariants here; CI fails if an invariant has no tagged tests.

**Financial (INV-F):**
- INV-F1 Every journal entry balances: Σdebits = Σcredits, per currency, to the minor unit.
- INV-F2 Posted financial documents are immutable; corrections are reversing/compensating events only.
- INV-F3 No posting into a closed period; period close is monotonic (reopen = privileged, audited, reversible event).
- INV-F4 Money is integer minor units + ISO-4217; no floats anywhere in a money path; allocation never creates or destroys a cent (Σparts = whole).
- INV-F5 Every financially-relevant document posts to GL through its declared template; no direct ledger writes outside the posting pipeline.
- INV-F6 Document number sequences are gapless-per-policy and assigned only at server acceptance.
- INV-F7 Stock quantity × valuation reconciles with GL inventory accounts at all times (projection lag bounded).
- INV-F8 Settlement never exceeds the document it settles: Σapplied ≤ gross, no negative application.

**Event store (INV-E):**
- INV-E1 Streams are append-only; no UPDATE/DELETE on the events table (DB grants + triggers make it impossible, not just forbidden).
- INV-E2 Optimistic concurrency: version conflicts are rejected, never silently merged.
- INV-E3 Events are immutable post-commit; schema evolution via upcasters only.
- INV-E4 command_id is unique: replay/retry produces exactly-once effects.
- INV-E5 Projections are pure functions of the log: rebuild(events) ≡ current projection, verified continuously by checksum.

**Tenancy & access (INV-T):**
- INV-T1 No query path returns another tenant's rows (RLS as backstop; zero rows without tenant context).
- INV-T2 No write path executes without an authenticated principal and authorization decision.
- INV-T3 Permission floors, approval gates, and declared value domains cannot be widened by overlays, plugins, or agents (ADR-014 constitution). Permissions are a floor and option sets are a ceiling; both express the same rule — the core layer's declaration is a bound no later layer may escape.
- INV-T4 Every mutation is attributable: actor, command, timestamp — no anonymous writes, including system/agent/plugin writes.
- INV-T5 Every stored field value conforms to its object's effective schema — declared type and declared option set; no write path stores a value outside it (online, offline replay, bulk import, or agent).

**Sync (INV-S):**
- INV-S1 No acknowledged write is ever lost (RPO 0).
- INV-S2 Offline commands pass the identical validation pipeline as online writes — no privileged sync side door.
- INV-S3 Client replica converges to server state; divergence is detected and repaired, never ignored.
- INV-S4 Rejected commands are surfaced to the user; no silent drops.
- INV-S5 No committed change is skipped by the change feed: for any cursor position a reader observes every committed entry exactly once, in a stable total order that does not change on resume. (The downstream half of INV-S1, enforced from WP-2.1 — the feed exists before the replica does.)

**Device (INV-D):**
- INV-D1 A device marked wiped is refused on every authenticated path — no request it can make both succeeds and skips the check. (Enforced from WP-2.5 in the authenticator, not at any endpoint: a control the subject can decline to receive is not one. Note what it deliberately does *not* claim — that the device deleted anything. The server proves refusal and delivery; erasure happens on a disk it does not own. At-rest protection of the replica itself is [ADR-021](adr/ADR-021-replica-at-rest-encryption.md) and WP-4.8. INV-D1 is also why a wipe is the one authentication outcome allowed to be distinguishable from the deliberately-opaque "session invalid": a client that cannot tell a wipe from an expiry does not delete anything.)

**Secret material (INV-K):**
- INV-K1 Secret material is never persisted, logged, emitted or replicated in plaintext: every stored secret is ciphertext under a per-secret data key wrapped by the deployment's key-encryption key, and no path outside `kernel/secrets` returns it. (Enforced from WP-3.0. Nothing already here covered it — INV-T1 is cross-tenant reads and INV-T4 is attribution — so the vault registers its own rather than borrowing one. The load-bearing half is *structural*, in the shape of INV-S2's: no route returns a secret's value, asserted against the live mux and the action table, so a reveal endpoint fails CI rather than review. K is key material; **P** is reserved for docs/20's privacy invariants.)

**Extension & autonomy (INV-X):**
- INV-X1 Plugins touch data only via capability-checked host functions — no ambient authority; a plugin cannot violate INV-F/E/T/S even if maliciously constructed.
- INV-X2 Plugin/hook failure never corrupts or partially commits a transaction.
- INV-X3 Agent/AI writes go through the same command pipeline, permissions, and approval gates as human writes — always (no "AI mode" bypass).
- INV-X4 No autonomous process (L0–L4) can modify invariant-enforcement code, this catalog, or its test suites.
- INV-X5 Migration/import writes obey every invariant above; bulk paths get no shortcuts (they get batching, not bypasses).

## 2. Enforcement layers (defense in depth — a violation must beat all four)

1. **Type system & codegen:** money types, tenant-scoped repositories, generated parameterized queries — entire bug classes unrepresentable.
2. **Storage layer:** DB constraints, RLS, append-only grants/triggers on event tables, CHECK constraints for balance where expressible. The database refuses what the application forgot.
3. **Command pipeline:** single choke point for all writes (UI, API, sync replay, plugins, agents, migrations). If a write didn't come through it, it didn't happen — enforced by DB role separation (app role has no direct DML on protected tables outside pipeline-owned functions).
   - **Deploying it (WP-1.10):** the grants are applied by `lasterp harden`, run as the schema owner after `lasterp migrate`; the server then connects as the restricted role. `lasterp doctor` reports whether a running deployment is actually separated and exits non-zero when it is not. Before WP-1.10 these grants existed only inside the test harness, which meant this layer was real in CI and absent in production — see [phase-1-review.md](notes/phase-1-review.md) P1 item 6. Deployment sequence and rationale: [docs/09](09-SCALABILITY-DEPLOYMENT.md#database-roles-required-on-postgres--wp-110).
4. **Runtime sentinels:** continuous verification (docs/13) — projection checksums vs event-fold, trial-balance audits, orphan scans, cross-tenant canary probes. Detection is a feature: a violation that slips through layers 1–3 is caught in minutes, quarantined, and auto-filed as a P0.

## 3. The Integrity Gauntlet (CI — exhaustive by policy)

A dedicated, non-skippable CI stage. **Every PR runs it. Every plugin submission runs it. Every L2/L3/L4 autonomous change runs it. No green gauntlet, no merge/install/apply — no exceptions, including hotfixes.**

| Suite | What it does |
|---|---|
| Invariant property tests | Randomized operation sequences (property-based, high iteration count nightly) asserting every INV-* holds; each invariant ID must have ≥1 tagged property |
| Adversarial writer suite | Attempts every known bypass: raw SQL to protected tables, unbalanced entries, closed-period posts, cross-tenant reads/writes, UPDATE on events, float money, pipeline-skipping writes — all must fail |
| Hostile plugin suite | Malicious WASM corpus (exfiltration, capability escalation, resource bombs, partial-commit attempts) against INV-X1/X2. *Shipped in WP-3.1a (`kernel/plugins/plugins_test.go` + `internal/app/plugins_integrity_test.go`), carrying **INV-X1**.* The corpus is **readable Go in `kernel/plugins/testdata/`, compiled to `wasip1/wasm` at test time by the toolchain the repo already pins** — not committed `.wasm`, because a corpus of opaque blobs is one nobody can review and "is this still hostile?" stops being an answerable question; and not TinyGo, because a second toolchain in CI is a dependency in everything but name. Five members: an infinite loop (contained by the wall-clock deadline, asserted to have *reached* the deadline rather than returning early), a memory bomb (contained by the page cap, and checked to still fail under a larger cap so the adversary is proven to be allocating), a thief importing host functions its manifest never requested (contained at **instantiation** — the host-function table is built from approved capabilities, so an ungranted import has nothing to bind to), an escape attempt against the filesystem, environment and network (which *reports* each refusal, so a plugin that crashed early cannot be mistaken for containment, with a real `LASTERP_DSN` set in the parent process so "not set" is evidence of isolation), and a chatty plugin exhausting the host-call budget. **WP-3.1b added the hook half, carrying INV-X2** (`kernel/plugins/hooks_test.go`, `runner_test.go`, `internal/app/hooks_integrity_test.go`): a sixth corpus member that vetoes, enriches, tries to enrich *past the schema*, fails on purpose, and writes a record from inside its own async hook. INV-X2 is proven **structurally** rather than by hunting a partial commit — sync hooks dispatch before CRUD opens its transaction, and the test runs an independent write from another goroutine while a hook is executing, which could not complete if the write's transaction were held across dispatch. The rest is the failure surface: a broken hook rejects by default and only a hook that declared `on_failure: allow` is ever skipped by an open breaker (skipping a fail-closed rule exactly when its plugin misbehaves is the failure mode); an enrichment is re-validated so a hook cannot store a value the schema forbids (INV-T5); a delivery that fails every retry is filed as a dead letter and the cursor moves on, because a queue head retrying forever is the stall INV-S4 counts as a silent drop; and a plugin does not react to its own writes, asserted over ten delivery passes with a non-vacuity check that the plugin really did write something to suppress. **WP-3.2a added the two public surfaces** (`kernel/plugins/http_test.go`, `endpoints_test.go`, `internal/app/ext_integrity_test.go`), extending **INV-X1** to the network and to inbound routes with a seventh corpus member that fetches whatever it is told to, carries a vault secret out to its allowlisted host, serves an endpoint, and returns a response no server should pass through. The load-bearing property is not the allowlist but *where it is checked*: the guard runs in the dialer, on the address actually being connected to, so an approved DNS name that resolves to `169.254.169.254` or `127.0.0.1` is refused at the socket — with the mirrored non-vacuity check that the same call succeeds once the deployment opts into private destinations, or the refusal would only mean the test server was unreachable. Redirects are asserted *not* followed (the one-hop allowlist bypass), every call is asserted audited exactly once with the query string absent, and the INV-K1 sweep is extended through the new path: a plugin that reads `acme_api_key` and sends it as a bearer token is checked to have really sent it before the audit log is searched for it, raw and base64. Inbound, the caller's session is proven necessary and `plugin:invoke` proven insufficient-without, a read-only plugin is proven unable to write on a fully-granted caller's authority (INV-T3), and what an endpoint writes names the plugin (INV-T4). **WP-3.2b added the supply chain and the author's half** (`kernel/plugins/bundle_test.go`, `author_test.go`, `internal/app/bundle_integrity_test.go`, `examples_integrity_test.go`): a bundle signed by a stranger, by nobody, or by the right key id carrying the wrong key is refused; a swapped module or a *widened manifest* under a valid signature is refused, which is the property the whole format exists for; tar entries that traverse, nest or are not regular files are refused rather than sanitised. It also carries **INV-F5 into the plugin surface** — a plugin may read an `Invoice` and a manifest asking to *write* one is refused at install, naming the invariant, because writes belong to invoicing's posting pipeline and generic CRUD would be the side door around it. Both example plugins are built from source and driven end to end on both dialects, including the redelivery pass that proves their at-least-once dedupe, and the notifier's vaulted webhook URL is swept out of the audit trail afterwards (INV-K1) — which is what found that the *path* of a webhook is itself a credential, so only its first segment is recorded. |
| Hostile agent suite | Red-team agent scenarios (prompt-injected goals: "bypass approval", "post directly", "widen own permissions") against INV-X3/X4 |
| Sync simulation harness | N clients × partitions/crashes/reorderings × INV-S properties (docs/04). *Shipped in WP-2.3a (`internal/app/sync_simulation_integrity_test.go`): four concurrent replicas on both dialects under injected partitions and mid-transaction crashes, carrying INV-S3/S5. Every injected fault is asserted to have fired — a fault-injection suite that quietly stops injecting still reports green. **WP-2.3b added the upstream half**: every client also writes offline between rounds, so a partitioned client is one holding work it could not send, and the fleet's delivered work is counted exactly afterwards — too few is a lost write, too many is a duplicated one (INV-S1/E4). One crash window is isolated separately (`--kill-after-command`), between the server committing and the client's record of it becoming durable, because nothing else reaches it. Conservation — commands in = accepted + filed — carries INV-S4, and INV-S2 is structural: `internal/app/sync_outbox_integrity_test.go` asserts no write endpoint exists under `/api/v1/sync`, in the action table and on the live mux. **WP-2.4 added the entitlement-change scenarios** (`internal/app/sync_scope_integrity_test.go`): a grant withdrawn or added between two syncs of the same replica, on both dialects, carrying INV-S1/S3/S4 and INV-T1/T2. The load-bearing one is `TestPurgeNeverDeletesQueuedWork`, whose scenario is built so the purge runs while the outbox is **non-empty** — with everything acceptable the drain empties the queue first and a purge that deleted `_outbox` outright would pass unnoticed, so both `read` and `create` are withdrawn and the drain's stop-on-reject leaves successors queued across it. Verified by mutation: making the purge delete `_outbox` turns it red. **WP-2.5 added the device-security scenarios** (`internal/app/device_integrity_test.go`), carrying the new **INV-D1**: a wiped device is refused on every authenticated path, enumerated off the live action table rather than spot-checked, with a pre-wipe assertion that the device could reach those routes at all so the refusal is not vacuous. The wipe is also driven end to end through the real replica — hydrate, wipe, reconnect, and the driver must *report* the wipe (`lasterp-device-wiped`) rather than the harness inferring it from an empty dump, since an empty replica is also what a driver that never synced produces. Mutation-checked: neutering `wipeReplica` turns both AC tests red. A wipe destroying queued commands is the one sanctioned exception to INV-S4 and is noted in the catalog entry itself; `TestScopePurgeStillSparesUnsentWork` is its paired regression, so a change to the wipe path that leaked into the purge path fails.*|
| Secret-material sweep | *Shipped in WP-3.0 (`internal/app/secrets_integrity_test.go`, `kernel/secrets/secrets_test.go`), carrying the new **INV-K1**.* Stores a known secret, then searches for it — raw **and base64**, since the columns are base64 and a raw-only search would call an unencrypted vault green — in the `secrets` row itself, the audit log, the event store, the change feed, a sync hydration page, a report export, and the body of every GET the server routes with the path parameters filled in with the secret's own name. Non-vacuity is asserted, not assumed: a canary contact must be *present* in the feed and snapshot probes, or the sweep is measuring an empty response. The structural half is `TestNoRouteReturnsASecret` (the action table plus reveal-shaped probes against the live mux). Mutation-checked: storing the value unsealed turns the round-trip test red on both dialects. **WP-3.2a extended it to the plugin network path**: the audit row an outbound call writes records method, host and path and never headers, bodies or the query string, so a plugin's own credential cannot land in the trail of the call that used it. |
| Concurrency torture | Parallel writers on hot streams/documents; INV-E2/E4 under contention |
| Fuzzing | All parsers (bank files, imports, API payloads, plugin manifests): malformed input may be rejected, never corrupt state |
| Golden files | Tax, payroll, report, posting-template calculations vs certified expected outputs |
| Adapter conformance | Full suite on Postgres AND SQLite — identical semantics or the build fails |
| Migration integrity | Every schema migration round-trips on seeded data with pre/post invariant checks + checksum manifests |
| Mutation testing (nightly) | Mutate invariant-enforcement code; if the test suite doesn't catch the mutant, the suite is inadequate — build fails |
| Chaos (nightly) | Kill nodes/DB failover mid-commit; INV-S1/E1 must hold after recovery |

**Coverage policy:** invariant-enforcement code requires 100% branch coverage + mutation score threshold (≥85%); "never weaken/delete a failing invariant test" (CLAUDE.md) is enforced by CODEOWNERS on `kernel/integrity/` + the gauntlet definitions — changes there need two human maintainer approvals and are outside every autonomous path (INV-X4).

## 4. Runtime posture
Sentinels run in production on schedule + sampling; any INV violation → automatic quarantine of the offending path, P0 task with forensic bundle (docs/12), tenant-visible integrity status page. The event log + hash-chained audit trails make every incident reconstructable. Integrity incidents are the only class where the system is biased to *stop* rather than degrade gracefully.
