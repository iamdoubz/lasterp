## Phase 2 — Sync & offline
- **WP-2.1 Change feed service:** logical-replication tail → NATS, scope tagging, cursored streams. AC: feed ordering + resume tests.
- **WP-2.2 Client replica** — **split into two PRs** (see [decisions](notes/WP-2.2-decisions.md), same precedent as WP-1.6): **PR-A (WP-2.2a) server sync API** — the half a replica cannot exist without, because WP-2.1's feed is a *pointer* log (`source` + `ref_id`, no payloads) and a client that learns "Invoice 019f… changed" still has no invoice. Lands materialization (`GET /api/v1/sync/changes?include=rows`, resolving pointers to current row state in one round trip, **re-authorized per object kind** — the pointer design was what bounded an over-broad `sync:read` in WP-2.1 and this removes that bound), a paged snapshot for hydration at a consistent feed position (`CRUD.List` returns every row for a tenant with no paging), and archived rows conveyed rather than filtered — `List` hides them, which is right for a UI and a permanent divergence for a replica. **PR-B (WP-2.2b) client replica** — SQLite-WASM/OPFS schema generation from `/meta/objects` (never a hand-written mirror, per ADR-006 + [ADR-017](adr/ADR-017-sync-client-core.md)), hydration, incremental apply on the WP-2.6 core, and the worker boundary ADR-017 §Consequences requires. **INV-S3 flips to TestRequired in PR-B**, where convergence is provable; PR-A carries INV-T1/T2 on its new read paths. AC: replica-converges-to-projection property test — randomized operations against the real binary with the replica on `node:sqlite`, plus one pass in a browser over OPFS in a worker. **Both PRs merged.** B's decisions: [WP-2.2b-decisions.md](notes/WP-2.2b-decisions.md) — which revises WP-2.2 §6 (money mirrors the server's single exact-string column, not two), adds `persistence` to `/meta/objects` (a replica generating its schema from metadata could not otherwise tell which objects it may hydrate), and guards the AC with a mutation check that deletes feed entries and requires convergence to fail.
- **WP-2.3 Outbox & command replay:** optimistic apply, pending flags, replay pipeline, accept/reject/rebase, conflict tray UI. AC: simulation harness (04-SYNC-ENGINE.md test plan) green; no-silent-loss property. **Read [WP-2.2b-decisions.md](notes/WP-2.2b-decisions.md) §5, §7 and §10 before starting — three things this WP inherits rather than discovers.** (a) The `_outbox` is the first thing in the client the server cannot reconstruct, so ADR-017's "a corrupted replica just re-hydrates" stops covering it: parse outbox rows at the port boundary rather than casting, and decide what happens when `navigator.storage.persist()` is **denied** before accepting a single offline write — browsers evict OPFS without warning and iOS evicts on inactivity. (b) Multi-tab is detected but not coordinated; two writers on one outbox is a correctness problem, not a usability one. (c) The reconnect *order* — downstream apply vs outbox drain vs (later) WP-2.4's revocation purge — is undesigned, and a purge that runs before a drain deletes the rows pending commands reference. Also note this WP is materially larger than its one roadmap line suggests: the simulation harness is infrastructure gating its own AC, and is worth landing separately against the existing read-only replica first. **Split into two PRs accordingly** ([decisions](notes/WP-2.3-decisions.md) §0): **PR-A (WP-2.3a) the simulation harness** — docs/04 §Test plan's "N virtual clients × scripted partitions/crashes/interleavings", grown out of `TestReplicaConvergesToProjection` rather than built beside it, carrying INV-S3/S5 under fault. **PR-B (WP-2.3b) the outbox — DONE** — `_outbox`, optimistic apply, drain, conflict tray; INV-S1/S2/S4 flipped to TestRequired, proven by upstream scenarios added to A's harness (every client writes offline between rounds; delivered work counted exactly) plus `internal/app/sync_outbox_integrity_test.go`. Also lands the one server change the design needs (a client-supplied UUIDv7 row id, §2) and two defects the harness found outside this WP's code: a `SQLITE_BUSY` on session validation surfaced as a **401** rather than a retry, and the crash injection counted optimistic writes as apply writes. Screens still write online-first (§13). Decided in A: a command is a stored HTTP request replayed through the ordinary gateway, so there is no sync write endpoint and INV-S2 has no way to be violated (§1); the server accepts a client-supplied UUIDv7 row id so an optimistic row needs no rewrite (§2); reconnect order is drain → hydrate → pull, with WP-2.4's purge after (§4); multi-tab needs no leader election because the VFS handle is already exclusive (§5); a denied `navigator.storage.persist()` warns and caps the outbox rather than refusing offline writes (§6).
- **WP-2.4 Scope management — DONE:** role-based scope computation, re-shape on change, revocation purge. A scope is the set of scope keys a principal may read (`GET /api/v1/sync/scope`), and the feed is filtered to it — **pointers included**, which supersedes WP-2.1's "an over-broad `sync:read` is bounded because a pointer is weaker than a row" and WP-2.2 §3's deliberate asymmetry. The re-shape is a diff of that list against `_hydration` (the replica already records what it holds), so there is no scope version and no server-side purge instruction queue — both of which docs/04 §Downstream 4 describes and neither of which buys anything over one round trip the reconnect was making anyway. Two things it was told to get right and did: **a purge deletes replicated rows and never `_outbox`/`_conflicts`** (the row is a copy of the server's, the queued command is work nothing reconstructs), proven by a test whose scenario forces the purge to run over a live queue; and **the tray still renders work for an object the user can no longer read**, because it shows the stored command and the server's problem+json rather than joining to the replica. Also lands two consequences of filtering: a short page reports the feed's **high-water mark** as its resume position (read before the page, safe under the ordering lock) so a scoped client never re-scans or stops short, and `applyPage` takes the server's cursor when ahead and **refuses** it when behind an entry the same page delivered. Corrects `order.go`'s stated upgrade path: a per-scope lock is *not* the feed's relief valve — per-scope ordering under one global cursor re-creates the INV-S5 stranding it exists to prevent, and doing it properly means per-scope *cursors*, a rewrite of the reader, `_sync_state`, the ack path and INV-S5's wording. Not built: row-level/conditional scopes (need `authz` condition evaluation) and per-device scopes (WP-2.5). Decisions: [WP-2.4-decisions.md](notes/WP-2.4-decisions.md). AC: entitlement-change scenarios — revocation purges, a new grant hydrates, and the replica converges to the *scoped* projection, on both dialects.
- **WP-2.5 Device security — DONE (one AC moved, deliberately and with an ADR):** device registration, per-device revocation, remote wipe. Devices become entities (`devices`, registered implicitly at session issue — an enrolment call a client can skip leaves an untracked replica), manageable at `GET /api/v1/devices` + `POST /api/v1/devices/{id}/{wipe,revoke}`. **The wipe signal rides the authenticator, not an endpoint:** a polling route or a field on the sync response can be skipped by the client, and a control the subject can decline to receive is not one — so a wiped device is refused on *every* authenticated path, which is the new **INV-D1**. It is the one 401 allowed to say why (`type: "device-wiped"`), because a client that cannot tell a wipe from an expiry signs the user out and leaves the replica on disk; correspondingly a wipe does **not** revoke the device's sessions, or `ValidateSession` would fail first and the instruction would never arrive. A wipe **destroys unsent work**, the deliberate opposite of WP-2.4's scope purge (the device is presumed hostile), and both rules carry a test naming the other. Delivery is recorded, never confirmed — nothing can prove erasure on a disk we do not own. **The second AC, "replica unreadable without keystore", is NOT delivered and is moved to WP-4.8 by [ADR-021](adr/ADR-021-replica-at-rest-encryption.md)**: ADR-017 fixed the browser on SQLite-WASM's SAH-pool VFS, whose sync `xRead`/`xWrite` cannot call async WebCrypto, so any page cipher needs extractable key bytes sitting next to the ciphertext — it would satisfy the sentence in docs/08 and not its intent. docs/08 §Data protection and its threat table are amended to state what actually protects a browser replica. Decisions: [WP-2.5-decisions.md](notes/WP-2.5-decisions.md). AC: wipe honored on reconnect — **pass**, end to end through the real replica on both dialects, mutation-checked.
- **WP-2.6 Spike: shared sync-client core** (TS lib vs Rust/WASM lib for web+Tauri+mobile) — **DONE**, output [ADR-017](adr/ADR-017-sync-client-core.md): TypeScript, one core per shell, replica in a dedicated worker (an OPFS constraint, not a language one). Prototype in `web/src/sync/` is WP-2.2's seed. Decisions: [WP-2.6-decisions.md](notes/WP-2.6-decisions.md).
- **WP-2.7 Offline-first screens — DONE** (added by [phase-2-review.md](notes/phase-2-review.md) P1.2, gated M2). The replica is now the read path for every metadata-driven screen — list, detail and edit — and `ObjectForm` writes through the outbox, so saving online and saving offline are the same code reaching the same route; only the delay before the drain differs. **There is deliberately no API fallback for data**: two read paths that can disagree is the divergence INV-S3 exists to prevent, and a fallback hides it rather than removing it. Schema and session *are* allowed a fallback to the replica's `_meta` cache, because that cache is the server's own last answer — one source, one cache — which is what lets the navigation render offline. Pending rows are flagged from the existing `_pending` sidecar rather than a second source of truth. **Running the script found four defects every existing suite passed over** ([decisions](notes/WP-2.7-decisions.md) §7), the first of them fatal to the entire phase in production: the CSP's `script-src 'self'` refused `WebAssembly.instantiate`, so the sync worker died on load in the shipped app while every headless and browser-harness test passed — fixed with `'wasm-unsafe-eval'`, which permits WASM compilation only and does not restore `eval()`. Also: reloading offline failed at the *document* request (fixed with a hand-written service worker that never caches `/api/v1/`), the app signed the user out on any probe failure rather than only a 401 (the same "could not check is not not-authenticated" rule the gateway already applies server-side), and the nav could not render offline. Known follow-ups recorded in [decisions](notes/WP-2.7-decisions.md) §8: a refused write shows a raw `conform` message where the server used to return localized problem+json; `scripts/e2e-server.sh` rebuilds the bundle only when `dist/index.html` is missing, so e2e can silently test stale code. AC: **pass** — the script runs end to end with the network off and converges on reconnect, in Chromium over OPFS, with the guard asserting no screen reads object rows from the API.
- **Milestone M2: "work all day offline, sync perfectly"** — the Lotus Notes demo. **The script passes as of WP-2.7.** What it covers is a chart-of-accounts and CRM day (Account and Contact, the two objects `crudObjects()` publishes), which is the first two rows of docs/04's offline-allowed list. What it does not: invoices, which are not in the replica, and GL posting, which docs/04 keeps online-required by default — both deliberately out of scope and both recorded in the script's §Not covered rather than quietly assumed.

## Phase 3 — Extensibility & AI
- **WP-3.0 Secrets vault — DONE.** `kernel/secrets`: per-secret AES-256-GCM data key, wrapped by a deployment key-encryption key from a pluggable `KeySource`, in a tenant-scoped RLS table. Lands the new **INV-K1** (docs/19) — nothing in the catalog covered "never stored in the clear", since INV-T1 is cross-tenant reads and INV-T4 is attribution. The per-secret data key is chosen by the rotation AC: rotation re-wraps one short column and the ciphertext is asserted byte-identical afterwards. Both seals bind their row as AAD, so a row lifted into another tenant fails to open — under RLS, not instead of it. **There is deliberately no route that returns a value** ([decisions](notes/WP-3.0-decisions.md) §4): the API stores, lists metadata and deletes, and `TestNoRouteReturnsASecret` enumerates the live mux so a reveal endpoint fails CI rather than review. Reads are server-side through `secrets.Get`, which requires a named reader and audits in the same transaction; the manifest capability check is the `Grants` seam **WP-3.1** fills, so INV-X1 is not claimed early. A secret is a kernel table rather than a metadata object, which is what keeps it out of the feed, the replica and every export structurally. **Two things it deliberately does not ship** (§2, §9): a KMS `KeySource` (a cloud SDK is a new runtime dependency for a deployment shape nobody runs yet — the interface is three methods) and the age file format (`filippo.io/age` for what we would use as a bag of bytes; a key file is the self-host shape docs/08 means). Operator steps in [docs/09](09-SCALABILITY-DEPLOYMENT.md) §Secrets key file. AC: **all pass** on both dialects, mutation-checked. Two named-owner deferrals it creates, recorded here so they stop living in a decisions file — **TOTP secrets at rest** (per-user column encryption, a different shape from a keyed store; owner: the WP that lands field-level encryption) and **per-tenant OIDC provider configuration** (now unblocked, and a WP of its own — routes, discovery cache and login-path changes; see [WP-1.9-decisions.md](notes/WP-1.9-decisions.md) §2).
- **WP-3.1 Plugin host** — **split into two PRs** ([decisions](notes/WP-3.1-decisions.md) §0; same precedent as WP-1.6/2.2/2.3): one line covering a sandbox, an authorization model, an install lifecycle, dispatch inside the write path and a failure policy is not one PR, and the halves carry different risk — *containment* and *transaction safety*.
  - **PR-A (WP-3.1a) the sandbox and the capability model — DONE.** `kernel/plugins`: manifest parsing, install/approval storage, the wazero+Extism runtime with its limits, the host-function surface, and the hostile corpus. **A plugin is its own principal** (`plugin:<id>`, never the triggering user — an audit row must name the plugin, and power that varies by caller cannot be reviewed at install time), and its authority is created once, at install, bounded by the approver's own grants: **a capability the approver does not hold refuses the install** rather than narrowing it silently (INV-T3). The principal is deliberately not a `users` row, so nothing can log in as a plugin. **INV-X1 flips to TestRequired here, and its enforcement turned out stronger than designed**: the host-function table *is* the module's import surface, so an ungranted function is not refused at call time — the module cannot be instantiated at all. The sandbox mounts no filesystem, exports no environment and allows no hosts; `http.request` is deliberately absent until there is an audited client, since ADR-007 requires every outbound call be audited and the built-in one is not (§4). Also corrects docs/05: **wazero has no CPU fuel meter** — the controls are the memory cap, the wall-clock deadline and a host-call budget (§2). AC: **pass** — infinite loop, memory bomb and exfiltration all contained, on a corpus that is readable Go compiled at test time rather than committed blobs (§5).
  - **PR-B (WP-3.1b) the hook surface — DONE** ([decisions](notes/WP-3.1b-decisions.md)); scope settled by a plan review before any code (see [WP-3.1-decisions.md](notes/WP-3.1-decisions.md) §8): `before_*`/`after_*` dispatch, veto semantics, async delivery, dead-letter, circuit breakers, and `kv.get/set`. Two design calls make the WP smaller than its roadmap line looked. **Sync hooks run before the transaction opens, never inside it** — a plugin holding SQLite's write lock for its whole budget is the throughput failure WP-2.3b already fought — which turns **INV-X2** into a *structural* invariant in the shape of INV-S2: no plugin code runs inside a transaction, asserted against the dispatch sites, rather than a runtime check hoping to catch a partial commit. And **async delivery rides the change feed** rather than a broker: `changefeed.Read` is already ordered, resumable and exactly-once-observed (INV-S5, since WP-2.1), so an `after_commit` runner is a feed consumer with a per-plugin cursor and solo mode stays one binary. Sync-hook latency is a tenant dial with a low default, a hard ceiling, a plain-language cost warning at approval, and per-plugin runtime attribution — the docs/09 p95 describes the system LastERP ships, and a slow plugin must read as *that plugin's* cost rather than as "the ERP is slow". A plugin does not react to its own writes (dispatch is suppressed for changes whose actor is that plugin) — which is why this WP **adds `actor_id` to `change_feed`**: without an author on the entry the runner cannot tell a plugin's output from anyone else's, and both publishers were already holding the actor and dropping it. INV-S5 is untouched by that column (ordering, cursors and resume semantics are unchanged). Two things building it found: a **delivery cursor created lazily on the first pass silently skips everything between the install and that pass**, so it is written at install instead; and a hook rejection needed a sentinel in `kernel/metadata` rather than `kernel/plugins`, because the gateway that must answer 422 knows about metadata and not about plugins. AC: **pass** on both dialects — veto, enrichment bounded by re-validation, fail-closed default with a declared `allow` opt-in, breaker that never skips a fail-closed hook, at-least-once delivery with dead letters, and self-suppression proven over ten passes with a non-vacuity check.
  - **Moved out of WP-3.1b by that review, each to an owner rather than to silence:** **`/ext/<plugin>/` endpoints → WP-3.2**, where the example plugins that would call them live (a plugin-declared route needs its own authz answer, and building the surface before a caller exists means guessing at it); **`enqueue_job` + the manifest's `schedule:` capability → WP-3.3**, which is where scheduled triggers arrive anyway and which supplies the job runner neither WP has; **`emit_event` → unscheduled**, because letting untrusted code write the event store is INV-E territory that deserves its own design rather than a line in a hook WP. A's manifest validation refuses all three by name, so an author is told which WP they are waiting on instead of installing something that silently never fires.
- **WP-3.2 PDKs + registry v1:** Rust/Go/TS/Python scaffolds, typed bindings codegen, signed bundles, install flow. **Also lands `/ext/<plugin>/` endpoints**, moved here from WP-3.1b by that WP's plan review: a plugin-declared HTTP route needs its own authorization answer (what gates it, and how an administrator sees what it exposes), and designing that surface before an example plugin exists to call it means guessing. The commission-calc and Slack-notifier examples below are that caller. Signature verification attaches to the module SHA-256 WP-3.1a already records and re-checks on every load. AC: afternoon-plugin tutorial completes; example plugins (commission calc, Slack notifier) pass.
- **WP-3.3 Automations:** trigger/condition/action workflows as metadata; CEL expressions — **includes activating CEL evaluation for RBAC condition grants** (stored-but-unevaluated since WP-0.3; until then only unconditional grants are honored). **Also owns the job runner**, moved here from WP-3.1b by that WP's plan review: scheduled triggers are an automation concept, and a runner built inside the plugin host would be a second scheduler the moment automations needed one. That runner is what unblocks the plugin manifest's **`schedule:`** capability and the **`enqueue_job`** host function, both refused by WP-3.1a with this WP named in the refusal.
